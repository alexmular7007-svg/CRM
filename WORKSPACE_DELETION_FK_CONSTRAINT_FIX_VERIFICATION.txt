PART 1: PROBLEM STATEMENT & ROOT CAUSE
═══════════════════════════════════════════════════════════════════════════════════

PRODUCTION ERROR:
┌─────────────────────────────────────────────────────────────────────────────────┐
│ ERROR: update or delete on table 'chat_messages' violates foreign key           │
│ constraint on table 'attachments'                                               │
│ Key(id)=168 is still referenced from table attachments.                         │
└─────────────────────────────────────────────────────────────────────────────────┘

ROOT CAUSE IDENTIFIED: Hibernate Persistence Context Issue
┌─────────────────────────────────────────────────────────────────────────────────┐
│ 1. @Modifying bulk delete methods were not clearing the L1 persistence cache   │
│ 2. Hibernate was holding stale entity references after delete operations        │
│ 3. PostgreSQL saw the cached state (entities still exist) not actual DB state   │
│ 4. FK constraint checks failed because Hibernate lied about what was deleted    │
│ 5. Even though deletion order was CORRECT, persistence context masked reality  │
└─────────────────────────────────────────────────────────────────────────────────┘

THE FIX:
┌─────────────────────────────────────────────────────────────────────────────────┐
│ BEFORE: @Modifying                                                              │
│         int deleteByWorkspaceId(@Param("workspaceId") Long workspaceId);       │
│                                                                                 │
│ AFTER:  @Modifying(clearAutomatically = true)    ← Key change!                │
│         int deleteByWorkspaceId(@Param("workspaceId") Long workspaceId);       │
│                                                                                 │
│ WHY: clearAutomatically=true tells Spring Data JPA to clear the L1 cache       │
│      after each bulk delete operation, forcing subsequent operations to see     │
│      the actual database state instead of cached entity references.             │
└─────────────────────────────────────────────────────────────────────────────────┘

WorkspaceServiceImpl.deleteWorkspace() executes in 7 PHASES:

PHASE 1: DELETE ATTACHMENTS FIRST (Leaf nodes with FKs to multiple parents)
┌──────────────────────────────────────────────────────────────────────────────────┐
│ AttachmentRepository.deleteAllByWorkspaceId(workspaceId)                        │
│   @Modifying(clearAutomatically = true)                                        │
│   @Query("DELETE FROM Attachment a WHERE a.workspace.id = :workspaceId")       │
│   SQL: DELETE FROM attachments WHERE workspace_id = ?                          │
│                                                                                 │
│ WHY FIRST:                                                                      │
│   • Attachments table has FKs to chat_messages AND tasks                       │
│   • If we delete ChatMessages first, orphaned attachment records remain        │
│   • PostgreSQL FK constraint: attachment.chat_message_id → chat_messages.id    │
│   • Orphaned records (chat_message_id NOT NULL but reference deleted) violate  │
│   • Must delete attachments BEFORE deleting either parent                      │
│                                                                                 │
│ RESULT: All attachment records deleted, persistence context cleared            │
