4. CURRENT ARCHITECTURE ANALYSIS
═══════════════════════════════════════════════════════════════════════════════

Existing Email Generation Flow:

Frontend (React)
  ↓ POST /api/emails/generate
  ↓ AIEmailGenerationRequest (DTO with validation)
Backend (Controller)
  ↓ AIEmailGenerationController.generateEmail()
  ↓
Backend (Service)
  ├─ AIEmailGenerationServiceImpl.generateEmail()
  ├─ constructs: prompt string
  ├─ calls: xaiProvider.generateResponseNoCache()
  └─
XAI Provider
  ├─ builds: HTTP POST request
  ├─ sets: Bearer auth, headers, JSON body
  ├─ calls: https://api.x.ai/v1/chat/completions
  ├─ receives: OpenAI-format response
  ├─ parses: JSON manually
  └─ returns: AIResponse (content, success, model)
  ↓
Service (continues)
  ├─ parses: AIResponse content as JSON
  ├─ extracts: subject, body
  ├─ generates: HTML email
  └─ returns: AIEmailGenerationResponse
  ↓
Controller
  └─ HTTP 200 with ApiResponse<AIEmailGenerationResponse>
  ↓
Frontend (React)
  ├─ receives: subject, bodyHtml, bodyPlainText, ctaText, ctaUrl
  └─ displays: preview modal for user review

6. ARCHITECTURAL SEPARATION VERIFICATION
═══════════════════════════════════════════════════════════════════════════════

GOOD NEWS: AI generation is already completely decoupled from campaign creation.

Email Generation Flow:
POST /api/emails/generate
  ↓ AIEmailGenerationController
  ↓ AIEmailGenerationServiceImpl.generateEmail()
  ↓ XAIProvider.generateResponseNoCache()
  ✓ Returns ONLY: subject, bodyHtml, bodyPlainText, ctaText, ctaUrl, metadata
  ✓ Does NOT call: EmailCampaignService, EmailCampaignRepository, mutations
  ✓ Does NOT trigger: campaign creation, onSuccess callbacks
  ✓ Result: Frontend receives email preview for manual user confirmation

Campaign Creation Flow (Separate):
POST /api/workspaces/{id}/email-campaigns
  ↓ EmailCampaignController
  ↓ EmailCampaignService.createCampaign()
  ↓ mutation.onSuccess() in EmailCampaignForm.jsx
  ✓ Returns ONLY: campaign metadata, tracking info
  ✓ Does NOT call: AI generation, email service

ISOLATION GUARANTEE:
✓ No shared state between AI generation and campaign creation
✓ No mutation/callback chains
✓ No implicit side effects
✓ Frontend controls the flow explicitly

9. SPRING AI IMPLEMENTATION STRATEGY
═══════════════════════════════════════════════════════════════════════════════

Architecture (After Migration):

Frontend (React)
  ↓ POST /api/emails/generate + AIEmailGenerationRequest
  ↓
Backend Controller (AIEmailGenerationController) - NO CHANGES
  ↓ validate request
  ↓
Backend Service (AIEmailGenerationServiceImpl) - REFACTORED
  ├─ construct prompt (same as before)
  ├─ call: ChatClient.prompt(prompt)
  │         .entity(EmailGenerationResponse.class)
  │         .call()
  │         .getResult()
  ├─ Spring AI handles:
  │  ├─ HTTP request building
  │  ├─ Authentication (Bearer token)
  │  ├─ Structured output deserialization
  │  ├─ Timeout handling
  │  ├─ Rate limit handling (429)
  │  ├─ Retry logic (exponential backoff)
  │  └─ Connection error fallbacks
  ├─ Service only handles:
  │  ├─ Prompt construction
  │  ├─ HTML email generation
  │  └─ Business logic validation
  └─
Spring AI ChatClient
  ├─ Connects to: https://api.x.ai/v1/chat/completions (or configured provider)
  ├─ Sends: OpenAI-format request (system message + user prompt)
  ├─ Receives: OpenAI-format response
  ├─ Deserializes: automatically to EmailGenerationResponse
  └─ Returns: response object with typed fields
  ↓
Backend Service (continues)
  ├─ Generates HTML email
  ├─ Builds AIEmailGenerationResponse
  └─ Returns
  ↓
Backend Controller
  ├─ HTTP 200 + ApiResponse<AIEmailGenerationResponse>
  ↓
Frontend (React)
  ├─ receives: subject, bodyHtml, bodyPlainText, ctaText, ctaUrl
  └─ displays: preview modal (unchanged)

Configuration (application.yml):
spring:
  ai:
    openai:  # Spring AI uses 'openai' for OpenAI-compatible providers
      api-key: \
      base-url: https://api.x.ai/v1
      model: grok-4.20-reasoning
      temperature: 0.7
      max-tokens: 1000
