[✓] #1. Database Schema Analysis

    - Feature tables: email_templates, email_campaigns, email_recipients
    - Automation tables: automations, automation_steps, automation_executions
    - Identified foreign key patterns and cascading delete behavior

[✓] #2. Critical Tables Documentation
    - 10 critical tables analyzed in detail
    - users (10K rows): Central hub, cascade on delete
    - workspaces (100-1K rows): Tenant isolation, workspace cascades all data
    - leads (10K-1M rows): Core business entity, soft-deleted on workspace delete
    - email_templates (50-500 rows): Reusable email definitions
    - email_campaigns (1K-100K rows): Batch send operations, cascade deletes recipients
    - email_campaign_recipients (1M-100M rows): Individual records, data transactional
    - email_campaign_history (5M-500M rows): Append-only webhook log, immutable
    - automations (100-10K rows): Workflow definitions, cascade to steps/executions
    - automation_steps (500-100K rows): Workflow nodes, cascade deleted with automation
    - automation_executions (1M-100M rows): Runtime tracking, execution history lost on cascade

[✓] #3. Foreign Key Relationships
    - Dependency map: users → workspaces → leads/campaigns/automations
    - Cascading delete behavior: Workspace deletion cascades to ALL tenant data
    - ON DELETE SET NULL: Campaign delete keeps recipient history
    - ON DELETE CASCADE: Automation delete loses execution history (audit trail)
    - Workspace isolation: Intentional cascade boundaries (safe)

[✓] #4. Backup Strategy
    - Current: Supabase auto-backup daily (7-day default retention)
    - Recommended: 3-tier backup strategy
      ├─ Hot (hourly): Supabase rolling 7-day window, PITR available
      ├─ Warm (daily): Export to S3, 30-day retention, $50-100/month
      └─ Cold (weekly): Glacier archive, 1-year retention, $5-20/month
    - RPO: 1 hour (acceptable for SaaS)
    - RTO: 2 hours (acceptable for production)
    - Encryption: AES-256 in transit and at rest
    - Retention: 7 days (hot), 30 days (warm), 1 year (cold), 7 years (compliance)

[✓] #5. Migration Strategy
    - Flyway executes migrations automatically on startup
    - Schema DDL: Hibernate auto-update enabled in production
    - Zero-downtime migrations: Add column, add index, rename column strategies
    - Data migration: Application-driven (not raw SQL)
    - Backward compatibility: New features work with old data (NULL defaults)
    - Downtime required: Type conversions, large table restructuring

[✓] #6. Recovery Strategy
    - Point-in-Time Recovery (PITR): Restore to any timestamp within retention window
    - Partial recovery: Restore specific tables to recovery database
    - Verification: 15-point checklist (row counts, constraints, indexes, data integrity)
    - Promotion: Swap recovery database with production (zero downtime possible)
    - Testing: Weekly staging restore to verify backup integrity

[✓] #7. Rollback Strategy
    - Application: Kubernetes/Railway rollback to previous version (5 min recovery)
    - Schema migration: Manual reversal of Flyway scripts + flyway_schema_history cleanup
    - Data rollback: Database restore from backup + application restore
    - Prevention: Keep previous Docker images, document each migration's undo
    - Recovery window: 30 days with soft-delete (no backup restore needed)

[✓] #8. Data-Loss Risks
    - 10 critical risks identified with probability/impact assessment
    - 🔴 CRITICAL (5):
        1. Cascading DELETE of workspace → all tenant data lost
        2. Cascading DELETE of campaign → all recipients/history lost
        3. Cascading DELETE of automation → all executions lost
        4. Backup corruption (test during restore)
        5. No soft-delete pattern (permanent loss on cascade)
    
    - 🟡 HIGH (3):
        6. Lead email collision (global → workspace-scoped migration)
        7. Connection pool exhaustion (HikariCP limits)
        8. Query performance degradation (index missing)
    
    - 🟠 MEDIUM (2):
        9. Storage capacity exhausted (1TB limit reached)
        10. Flyway script idempotency failure (script not reentrant)
    
    - Mitigation: Soft-delete flags + immutable history + comprehensive backups

[✓] #9. Safe Backup Procedures
    - 3 backup methods documented with code:
        A. Supabase Native: Daily automatic, included in plan, 7-day retention
        B. pg_dump to S3: Manual script, compression, encryption, tagging
        C. Logical Replication: Real-time replica, read traffic capable
    
    - Pre-backup: Capacity verification, credential validation, window scheduling
    - During: pg_dump or Supabase backup with progress monitoring
    - Post: Integrity verification, staging restore test, checksum validation
    - Monitoring: Daily backup age/size check, alert if > 24h old

[✓] #10. Recovery Procedures
    - PITR step-by-step (8 steps, 30-60 min recovery time)
    - Partial recovery (specific tables only)
    - Verification checklist (15 points)
    - Promotion procedure (swap recovery → production)
    - Testing: Runnable SQL scripts to verify table counts
    - Documentation: Pre-recovery decision tree

[✓] #11. Rollback Procedures
    - Application version: kubectl/Railway rollback (5 min)
    - Schema migration: Manual Flyway history cleanup + reverse SQL
    - Data rollback: Full backup restore procedure
    - Prevention: Document undo for each migration before deploying forward
    - Fallback: If manual rollback fails, use full database restore

[✓] #12. Testing Procedures
    - Backup Integrity Check (daily): 5 min check of backup size/timestamp/checksum
    - Staging Restore (weekly): 30 min full restore to staging DB, verify row counts

    - Disaster Recovery Drill (quarterly): 4 hour full simulation with app verification

CRITICAL FINDINGS & RISKS
================================================================================

🔴 CRITICAL RISKS:

1. WORKSPACE CASCADE DELETE
   Current: DELETE workspace → ALL tenant data deleted immediately
   Risk: Accidental workspace deletion = complete data loss
   Mitigation: (1) Soft-delete with 30-day recovery window
               (2) Point-in-time backup (PITR available with Supabase)
               (3) Require 2-factor confirmation before delete
   Status: NOT IMPLEMENTED (no soft-delete, no confirmation dialog)

2. EMAIL CAMPAIGN RECIPIENTS CASCADE DELETE
   Current: DELETE email_campaign → ALL recipients and history deleted
   Risk: Audit trail destroyed, email delivery metrics lost
   Mitigation: (1) Soft-delete campaign (deleted_at flag)
               (2) Archive recipients to cold storage
               (3) Immutable history table (never update, only insert)
   Status: NOT IMPLEMENTED

3. AUTOMATION EXECUTION HISTORY LOSS
   Current: DELETE automation → ALL executions deleted
   Risk: Cannot audit which leads went through which automation
   Mitigation: (1) Archive automations (archived_at flag)
               (2) Replicate executions to analytics warehouse
               (3) 2-year retention for execution history
   Status: NOT IMPLEMENTED

4. NO BACKUP RECOVERY SLA DEFINED
   Current: Supabase auto-backups exist, but no documented recovery time
   Risk: During incident, don't know if recovery possible
   Mitigation: (1) Document backup schedule (daily)
               (2) Document retention policy (30 days warm, 1 year cold)
               (3) Set RPO/RTO (1 hour RPO, 2 hour RTO)
               (4) Test recovery weekly (staging restore)
   Status: NOT DOCUMENTED

5. NO AUDIT LOG / CHANGE TRACKING
   Current: User A deletes lead; nobody knows when/why/how
   Risk: Compliance (GDPR/CCPA require audit trail)
   Mitigation: (1) Implement audit log table
               (2) Log all DML (INSERT/UPDATE/DELETE)
               (3) Track user, timestamp, old/new values
               (4) 7-year retention for legal holds
   Status: NOT IMPLEMENTED

🟡 HIGH RISKS:

6. BACKUP CORRUPTION (Test during restore)
   Current: Weekly backups taken, but never tested
   Risk: When needed, backup unrestorable (corrupted)
   Mitigation: (1) Test staging restore weekly (30 min)
               (2) Checksum verification
               (3) Multiple backup copies (Supabase + S3)
   Status: TESTING PROCEDURE DOCUMENTED, NOT EXECUTED

7. EMAIL CAMPAIGN METRICS MUTABLE
   Current: sent_count, delivered_count, opened_count can be updated
   Risk: Metrics not trustworthy (can be modified retroactively)
   Mitigation: (1) Make metrics immutable (increment only, no update)
               (2) Use email_campaign_history for source of truth
               (3) Aggregate metrics daily (snapshot table)
   Status: NOT IMPLEMENTED

8. CONNECTION POOL EXHAUSTION
   Current: HikariCP max-pool-size: 20
   Risk: Under load, all connections used, new queries wait/timeout
   Mitigation: (1) Monitor active connections (alert > 15)
               (2) Identify slow queries
               (3) Increase pool size if needed (trade-off: more memory)
   Status: MONITORING PROCEDURE DOCUMENTED, NOT CONFIGURED
